## 1) معمارية (Architecture)

### FI-01 — توحيد مصدر الحالة: إنهاء ازدواجية REST-globals / WS-SessionContext [MID]
- **من**: NF-03 / g5. REST يعمل على `fm`/globals عالميًّا وWS على SessionContext.
- **الفائدة**: إزالة أخطر سطح التباس (بحث/استعادة على مشروع غير المقصود)؛
  يفتح الطريق لتعدد المستخدمين لاحقًا.
- **الكلفة**: متوسطة–عالية — إعادة توجيه ~15 REST endpoint إلى مفهوم جلسة
  (رأس session-id أو حصر REST في القراءة فقط).
- **الشرط المسبق**: M3 مشحونة (سياسة project_id في السجل — TSK-302)؛ قرار
  منتج: هل REST المتحوّلة (switch-project/restore) تبقى أصلًا؟

### FI-02 — تفكيك server.py (god-module 2,613 سطرًا) [MID]
- **من**: g1. routes + WS + composition root + frame helpers في ملف واحد.
- **الفائدة**: خفض أكبر سطح تغيير مشترك؛ يقلص تصادم كل TSK مستقبلي.
- **الكلفة**: متوسطة — استخراج تدريجي: `routes_api.py` / `ws_dispatch.py` /
  `bootstrap.py`؛ goldens QA-T08 هي الحارس.
- **الشرط المسبق**: M1+M2 مشحونتان (لا يُنقل كود مكرر أو معطوب).

### FI-03 — انضباط الإيقاف (graceful shutdown) [SHORT]
- **من**: NF-05. خيوط runners كلها daemon بلا join.
- **الفائدة**: إيقاف نظيف — لا دفعة apply مقطوعة في المنتصف.
- **الكلفة**: منخفضة — إشارة إيقاف تعاونية عبر تذاكر السجل القائمة
  (`cancel()` جماعي + انتظار مهلة) في `main()`.
- **الشرط المسبق**: TSK-304 (نقاط تفتيش الإلغاء داخل الدفعات).

## 2) قابلية التوسع (Scalability)

### FI-04 — تفعيل درزة redis/worker الموجودة أصلًا [LONG]
- **من**: g9. `backends_from_config` (core/backends.py:L126) نقطة توسعة T-109
  جاهزة، وworker.py يملك ExecutionRegistry مستقلًا.
- **الفائدة**: أكثر من عملية/آلة؛ عزل أعطال runners عن عملية الويب.
- **الكلفة**: عالية — backend redis للسجل والناقل + اختبارات توزيعية.
- **الشرط المسبق**: FI-01 (حالة موحّدة قابلة للتسلسل)؛ TSK-303 (سجل مطهَّر).

### FI-05 — فهرسة تزايدية للمشاريع الضخمة [MID]
- **من**: امتداد TSK-501. الفهرس المشترك يبقى in-memory لكل مشروع.
- **الفائدة**: فتح مستودعات 50k+ ملف دون كلفة مسح أولي كاملة.
- **الكلفة**: متوسطة — persistence للفهرس (sqlite/msgpack) + إبطال بالخطافات.
- **الشرط المسبق**: TSK-501 مشحونة ومقاسة.

## 3) قابلية الصيانة (Maintainability)

### FI-06 — طبقة تسجيل موحّدة (structured logging) [SHORT]
- **من**: NF-14. اليوم: print + ابتلاع صامت.
- **الفائدة**: تشخيص أعطال الإنتاج؛ يُغني عن جولات "لماذا صمت النظام".
- **الكلفة**: منخفضة — logging.config + استبدال print تدريجيًا (يمكن آليًا).
- **الشرط المسبق**: TSK-305 (جرد مواضع except وتصنيفها) — يوفر الخريطة.

### FI-07 — تفكيك app.js (3,723 سطرًا) إلى ES modules [MID]
- **الفائدة**: نفس منطق FI-02 للواجهة؛ يمكّن اختبارات وحدات JS (QA-T11 آليًا
  بدل اليدوي).
- **الكلفة**: متوسطة — لا bundler حاليًا؛ يلزم قرار أدوات (vite أو ES modules
  خام) — بلا تغيير سلوك.
- **الشرط المسبق**: M4 مشحونة (لا يُنقل كود بث معطوب).

### FI-08 — أتمتة حراس الجودة في check.sh [SHORT]
- **من**: NF-24 + أنماط موجودة (check.sh يمنع ws.send خارج _WSAdapter).
- **الفائدة**: تثبيت مكاسب البرنامج: فحص دورات استيراد (QA-T14)، grep-guards
  للتعريف الواحد (MAX_SMART_FILE_SIZE، قائمة التجاهل الموحدة، yaml.safe_load).
- **الكلفة**: منخفضة جدًا — سكربتات grep/AST تُضاف للسلسلة القائمة.
- **الشرط المسبق**: M2 مشحونة.

- **الكلفة**: منخفضة — DOMPurify حول نقاط innerHTML الرئيسة.
- **الشرط المسبق**: — (مستقل).
