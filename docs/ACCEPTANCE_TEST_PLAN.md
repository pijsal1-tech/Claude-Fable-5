# ACCEPTANCE_TEST_PLAN — خطة اختبار قبول مرحلة D-19 (بإدارة المنفّذ)

> **الحاكمية**: طلب مالك مباشر (Session 112 تكملة 13): «عايزك تحدد أنت خطة
> الاختبار المناسبة للمرحلة دي... أريدك تدير عملية الاختبار بالكامل».
> هذه الوثيقة هي الخطة الرسمية. المنفّذ يدير الدورة: المالك ينفّذ اختبارات
> جهازه بالترتيب أدناه ويرسل المخرجات، والمنفّذ يحلّل ويحكم
> (ناجح / يحتاج إصلاح / ننتقل للتالي).

## 0) تقسيم العمل — مَن يختبر ماذا ولماذا (إجابة سؤال المالك المباشر)

**المبدأ الحاكم**: P-11 — لا ادعاء اختبار آلي لسلوك يتطلب نموذجًا حقيقيًا
أو متصفحًا حقيقيًا أو عتاد المالك الحقيقي.

| الفئة | الأنسب | السبب |
|---|---|---|
| البوابة الآلية الكاملة (mypy/flake8/pytest 2872) | **المنفّذ** | آلية بالكامل، تتكرر عند كل تغيير، Sandbox كافٍ |
| فحص دخاني حي REST + حارس التعريض الشبكي | **المنفّذ** | curl + خادم حقيقي في Sandbox يكفيان |
| خط أساس أداء Sandbox (perf_probe) | **المنفّذ** | مرجع المقارنة — نُفِّذ ورُسِّخ في runbook |
| قياس الأداء على العتاد الحقيقي (القرار 11) | **المالك حصرًا** | جوهر السؤال «بيئة أم كود؟» لا يُجاب إلا من جهازه |
| سلاسة الواجهة/FPS في متصفح حقيقي | **المالك حصرًا** | Sandbox بلا متصفح؛ FPS قياس بصري-تفاعلي (P-11) |
| E2E مع مزود ذكاء حقيقي (محادثة/agent) | **المالك حصرًا** | لا مفاتيح مزود حقيقية لدى المنفّذ (P-11) |
| توافق Windows | **المالك حصرًا** | بيئة الفحص هنا Linux — التدقيق الساكن تم (WINDOWS_COMPAT) |

**التوصية الصريحة**: التقسيم أعلاه — لا أحد «أفضل» مطلقًا؛ كلٌّ يغطي ما
لا يستطيعه الآخر. المنفّذ غطّى نصيبه كاملًا (§1) قبل تسليم الخطة، فما
تبقّى للمالك هو **فقط** ما يستحيل آليًا — ست اختبارات مرتّبة بالأولوية (§2).

## 2) نصيب المالك — بالترتيب حسب الأولوية

> **بروتوكول الإدارة**: نفّذ الاختبار رقم 1، أرسل مخرجاته كاملة (انسخ نص
> الطرفية أو التقط شاشة)، وانتظر حكم المنفّذ قبل الانتقال للتالي —
> إلا إذا نصّ الاختبار على أنه مستقل.

### 🥇 الاختبار 1 — perf_probe على جهازك الحقيقي (القرار 11 — الأعلى أولوية)

- **لماذا مهم**: هو الحكم النهائي في CEV-F-006 («رجفة» الواجهة): إن غابت
  الأرقام السيئة على جهازك ⇒ المشكلة بيئية (Sandbox بـ 2 vCPU) ونغلق
  البند؛ إن ظهرت ⇒ مشكلة أداء حقيقية ونفتح TSK إصلاح. كل بنود D-19
  الأخرى مغلقة — هذا بند المتابعة الوحيد المفتوح.
- **الهدف**: قياس زمن استيراد الخادم ومساري البحث على 5000 ملف بنفس
  عقد الاختبار الرسمي (أفضل-من-3، عتبة 1.0s حرفية).
- **الخطوات على جهازك**:
  1. `git pull` (أو استنساخ جديد) ثم من جذر المشروع:
  2. Windows: `py -3 scripts\perf_probe.py --json`
     · Linux/macOS: `python3 scripts/perf_probe.py --json`
  3. أرسل **كامل** المخرجات وخاصة سطر JSON الأخير.
- **النجاح المتوقع**: تقرير عربي + سطر JSON + خروج 0؛ زمنا البحث < 1.0s
  (على جهاز حديث نتوقع أفضل من خط أساس Sandbox: 0.160s / 0.134s).
- **الفشل المتوقع**: خروج 1 + «⛔ تجاوز» لأي مسار ≥ 1.0s ⇒ أرسل JSON
  وسيُفتح TSK إصلاح بالأرقام.
- **أخطاء شائعة**:
  - التشغيل من مجلد داخل OneDrive/Dropbox (مزامنة تلوث القياس) — انقل
    المشروع لمسار محلي صِرف.
  - مضاد الفيروسات يفحص 5000 ملف مؤقت لحظة إنشائها — أعد التشغيل مرة
    ثانية (القياس الثاني «دافئ» وأصدق).
  - وضع توفير الطاقة/بطارية منخفضة يخفّض تردد المعالج — شغّل موصولًا
    بالكهرباء.
  - تشغيله داخل IDE debugger بدل طرفية عادية.
  - نسيان `--json` (التقرير يظهر لكن سطر المقارنة الآلي يغيب).

### 🥈 الاختبار 2 — إقلاع حقيقي + جولة دخانية في المتصفح

- **لماذا مهم**: كل الفحص الآلي يمر عبر test client أو curl — لم يفتح أحد
  المحرر في متصفح حقيقي على HEAD الحالي بعد كل تغييرات D-19 (أذونات
  حية، مزودو API-key، ACP، حارس الشبكة). هذا أول «هل يعمل فعلًا؟».
- **الهدف**: التحقق أن الخادم يقلع، الواجهة تُحمَّل، وتدفق الثقة والفتح
  الأساسي سليم.
- **الخطوات**:
  1. `py -3 server.py` (يفتح على `http://127.0.0.1:5000`).
  2. افتح الرابط في المتصفح، افتح مشروعًا، ولاحظ **مطالبة الثقة**
     (Workspace Trust) — اقبلها.
  3. جرّب: فتح ملف، تحرير، حفظ، شجرة المشروع، بحث في الكود.
  4. افتح لوحة الأذونات وتأكد أنها ترسم القيم.
  5. أوقف بـ **Ctrl+C** (لا بإغلاق النافذة — WINDOWS_COMPAT §1).
- **النجاح**: صفحة تُحمَّل بلا أخطاء Console حمراء، الفتح/الحفظ/البحث
  تعمل، الأذونات تُعرض.
- **الفشل**: صفحة بيضاء / أخطاء Console / 500 في أي مسار ⇒ التقط شاشة
  لـ Console + آخر أسطر الطرفية وأرسلها.
- **أخطاء شائعة**: منفذ 5000 مشغول (أضف `--port 5001`)؛ فتح
  `0.0.0.0` بدل `127.0.0.1`؛ نسيان `pip install -r requirements.txt`
  بعد pull؛ كاش متصفح قديم (Ctrl+F5).

### 🥉 الاختبار 3 — سلاسة الواجهة وFPS (الشق اليدوي من القرار 11)

- **لماذا مهم**: perf_probe يقيس الخلفية فقط؛ «الرجفة» المشكو منها ظاهرة
  واجهة — لا تُقاس إلا بعينك + DevTools على جهازك (P-11).
- **الهدف**: حكم كمي على سلاسة الواجهة أثناء الاستخدام الفعلي.
- **الخطوات** (التفصيل الكامل في `docs/perf_probe_runbook.md` §4):
  1. أثناء تشغيل الاختبار 2: DevTools ▸ ⋮ ▸ More tools ▸ Rendering ▸
     فعّل **Frame Rendering Stats**.
  2. مرّر ملفًا طويلًا، اكتب بسرعة، بدّل تبويبات — راقب عدّاد FPS.
  3. Performance ▸ سجّل 10 ثوانٍ من الاستخدام ▸ ابحث عن Long Tasks
     (> 50ms) حمراء.
  4. راقب CPU/RAM لعملية python في Task Manager أثناء ذلك.
- **النجاح**: FPS يبقى فوق ~50 غالب الوقت ولا Long Tasks متكررة ⇒
  الرجفة كانت بيئية — **يُغلق CEV-F-006 نهائيًا**.
- **الفشل**: FPS يهبط دون ~30 باستمرار أو Long Tasks متسلسلة ⇒ صدّر
  ملف تسجيل Performance (زر Save profile) وأرسله ⇒ TSK إصلاح.
- **أخطاء شائعة**: قياس مع 40 تبويبًا مفتوحًا وامتدادات ثقيلة (جرّب نافذة
  خفيّة Incognito)؛ ترك DevTools مفتوحًا على تبويب يستهلك هو نفسه
  (أغلِق لوحات غير مستخدمة)؛ الخلط بين بطء أول تحميل (بارد) والرجفة
  المستمرة.

### 4 — E2E مع مزود ذكاء حقيقي (محادثة + agent)

- **لماذا مهم**: المنفّذ لا يملك مفاتيح مزود حقيقية — كل اختبارات
  المزودين آلية بمزود زائف. سلوك النموذج الحقيقي (بث، أدوات agent،
  بوابة الموافقة على الأوامر) لم يُشهد على HEAD الحالي.
- **الهدف**: تدفق كامل: سؤال → بث → استدعاء أداة → موافقة → نتيجة.
- **الخطوات**:
  1. اضبط مزودك المعتاد (أو مزود API-key عبر TSK-735 إن كنت تستخدمه).
  2. أرسل سؤالًا بسيطًا وتأكد من البث التدريجي.
  3. اطلب من الـ agent شيئًا يستدعي أداة قراءة (مثل «اعرض شجرة
     المشروع») ثم شيئًا يستدعي أمرًا (مثل «شغّل الاختبارات») —
     يجب أن تظهر **بوابة الموافقة** قبل تنفيذ الأمر.
  4. ارفض موافقة مرة واقبلها مرة — تحقق أن الرفض يُحترم.
- **النجاح**: بث سلس، أدوات تعمل، الموافقة تظهر وتُحترم قبولًا ورفضًا.
- **الفشل**: تعليق بلا رد / أمر نُفِّذ بلا موافقة (**بلّغ فورًا — أمني**) /
  خطأ مزود ⇒ أرسل `/api/diagnostics` + لقطة المحادثة.
- **أخطاء شائعة**: مفتاح مزود منتهٍ/حصة منتهية (تُشخَّص من diagnostics)؛
  اختبار الموافقة في مساحة غير موثوقة والاستغراب أن كل شيء يطلب موافقة
  (هذا الصحيح — راجع §1 الدرس 2).

### 5 — تحرير الأذونات حيًا من الواجهة (TSK-734 في متصفح حقيقي)

- **لماذا مهم**: أُثبت عبر REST (A4) لكن لوحة الواجهة نفسها لم تُختبر
  بيد بشرية على HEAD.
- **الهدف**: قلب `force_command_approval` وتعديل allowlist من اللوحة
  ورؤية الأثر **بلا إعادة تشغيل**.
- **الخطوات**: من لوحة الأذونات: فعّل إلزام الموافقة ← اطلب من الـ agent
  أمرًا كان مسموحًا تلقائيًا ← يجب أن يطلب موافقة الآن ← أعد الوضع.
- **النجاح**: الأثر فوري في نفس الجلسة، وملف `permissions_overrides.json`
  يظهر/يُحذف بجوار config.yaml (وconfig.yaml **لا يتغير بايتًا** أبدًا).
- **الفشل**: احتاج إعادة تشغيل ليسري الأثر، أو تغيّر config.yaml ⇒ بلّغ.
- **أخطاء شائعة**: التجربة في مساحة غير موثوقة (force ستبقى True مهما
  فعلت — سلوك صحيح)؛ توقّع أن مفاتيح غير المفتاحَين المسموحَين قابلة
  للتحرير (whitelist مقصود).

### 6 — قائمة فحص Windows (اختياري لكن موصى به مرة واحدة)

- **لماذا مهم**: قرار D-8-ب «Windows أولًا» والتدقيق الحالي ساكن من
  Linux — التحقق النهائي بيد المالك على Windows حقيقي.
- **الهدف/الخطوات**: نفّذ قائمة `docs/WINDOWS_COMPAT.md` §6 كما هي
  (مسارات، Ctrl+C، ألوان الطرفية، تشغيل desktop.py إن رغبت).
- **النجاح**: كل بنود §6 تمر. **الفشل**: أي بند يسقط ⇒ اسم البند +
  المخرجات.
- **أخطاء شائعة**: PowerShell قديم مع الترميز العربي (جرّب
  Windows Terminal)؛ `python` يشير لإصدار Store — استخدم `py -3`.
