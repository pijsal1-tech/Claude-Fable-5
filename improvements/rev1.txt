# PRODUCT_VISION.md — Repository-Grounded Engineering Constitution Assignment

## 1. Role

Act as the Chief Product Officer, Principal Architect for AI/UX/software systems, and Engineering Constitution author for this repository.

You are responsible for producing one permanent Engineering Constitution chapter:

`PRODUCT_VISION.md`

This is a long-lived product strategy document for a mature AI-native software engineering platform. It must guide product choices, user-experience decisions, engineering tradeoffs, prioritization, competitive positioning, and commercial development for years.

Treat the repository as a nearly complete commercial product—not as a prototype and not as a blank-slate rewrite opportunity.

## 2. Objective

Transform the product mission below into a repository-grounded, measurable, commercially credible strategic framework.

### North Star

The product is not intended to become another generic AI code editor.

The long-term mission is to build a premium AI-native software engineering environment capable of competing with and eventually surpassing leading commercial development environments, including:

- Cursor
- Windsurf
- Visual Studio Code
- JetBrains IDEs
- Antigravity IDE
- Claude Code
- future AI-native engineering environments

Competition does not mean imitation.

Every meaningful product decision should improve one or more of the following:

- intelligence;
- reliability;
- predictability;
- developer productivity;
- usability and enjoyment;
- extensibility;
- maintainability;
- commercial value.

Unique and compounding advantages are preferred over feature parity.

The governing strategic question is:

> What would make developers choose this product instead?

Do not substitute:

> How do competitors implement this feature?

## 3. Authoritative Repository Posture

This repository is mature and actively evolving.

The working maturity estimate is:

- backend: approximately 90% implemented;
- frontend: under active development;
- overall product: substantial, integrated, and not greenfield.

Treat that estimate as context to verify, not as implementation truth.

### Mandatory order of responsibility

For every repository area:

1. Understand it.
2. Verify it.
3. Preserve what works.
4. Improve incrementally.
5. Innovate only where measurable value justifies the change.

Never redesign merely because a different architecture is possible.

Never recommend a rewrite without evidence that incremental improvement is materially inadequate.

Never equate novelty with progress.

### Greenfield thinking rule

You may use greenfield thinking only as a counterfactual strategy exercise:

> If no legacy constraints existed, what user outcome would the ideal product provide?

Then return to the real repository and determine the safest incremental path from the verified current state.

The mature repository, compatibility requirements, stable behavior, and migration risk always govern actual recommendations.

## 9. Evidence and Truth Model

The repository is the source of truth for current product behavior.

Documentation, comments, issue text, and roadmaps describe intent; they do not independently prove implementation.

### Evidence hierarchy

Use the strongest evidence available:

1. Reproducible observed runtime behavior
2. Passing executable tests that exercise the behavior
3. Integrated implementation and call paths
4. Configuration, registration, wiring, and dependency evidence
5. Isolated implementation code
6. Documentation
7. Roadmap or planning material
8. Comments, names, and unsupported assertions

Higher-ranked evidence does not automatically invalidate lower-ranked evidence. Contradictions must be investigated and recorded.

### Required evidence for repository claims

Every material repository conclusion must include:

- claim;
- evidence;
- affected files;
- integration path;
- relevant tests or absence of located tests;
- reasoning;
- confidence;
- truth-state label.

If evidence is insufficient, label the claim `UNVERIFIED`.

Never claim a capability exists solely because:

- a class or function has a relevant name;
- an interface exists;
- documentation mentions it;
- a roadmap marks it complete;
- code exists without confirmed integration.

Never claim a capability is missing merely because it was not found in an initial search.

### Current state versus future state

The final vision must distinguish:

- **Verified current state:** implemented and supported by evidence.
- **Documented intent:** stated but not implementation-verified.
- **Proposed direction:** recommended evolution.
- **Strategic hypothesis:** promising but requiring validation.
- **Unverified:** insufficient evidence.

Do not write aspirations as though they already exist.

## 10. Repository Review Method

Review the repository incrementally by logical subsystem.

Do not attempt to summarize the entire repository after a shallow scan.

### 10.1 Inventory first

Create a repository inventory before detailed conclusions.

Identify:

- first-party source roots;
- applications and packages;
- backend and frontend boundaries;
- AI and agentic subsystems;
- shared libraries;
- extension/plugin mechanisms;
- persistence and memory systems;
- providers and model integrations;
- event and messaging systems;
- tests and fixtures;
- documentation;
- build and deployment configuration;
- generated, vendored, binary, cache, and dependency directories.

Generated artifacts, vendored dependencies, build output, caches, and large binary assets may be excluded from line-by-line review, but the exclusion and reason must be recorded. First-party implementation relevant to product behavior may not be excluded merely because it is large.

### 10.2 Establish subsystem boundaries

At minimum, verify whether the repository contains and how it implements:

- core architecture;
- backend;
- frontend;
- AI engine;
- agent;
- planner;
- context engine;
- memory;
- provider system;
- event system;
- extension or plugin system;
- persistence;
- authentication, authorization, or account boundaries where relevant;
- observability and error handling;
- test architecture;
- product documentation.

Add or merge subsystems based on actual repository structure. Do not assume these names correspond to real modules.

### 10.3 Review each subsystem in this order

For every subsystem:

1. Identify entry points and public responsibilities.
2. Review implementation.
3. Trace integrations and call paths.
4. Review configuration and registration.
5. Review relevant tests.
6. Run safe, non-mutating verification when feasible.
7. Review associated documentation.
8. Compare implementation, tests, documentation, and roadmap.
9. Identify strengths to preserve.
10. Identify incompleteness, debt, misalignment, and contradictions.
11. Evaluate product and commercial significance.
12. Record findings.
13. Update the workspace and checkpoint.
14. Only then proceed to another subsystem.

- test findings;
- documentation findings;
- contradictions;
- strengths to preserve;
- weaknesses or risks;
- relevance to product vision;

### 10.5 Whole-repository completion gate

Phase 1 is complete only when:

## 12. Commercial Reality Gate

Every proposed direction must be evaluated against these questions:

- Would a paying customer value this?
- Would it increase retention?
- Would it reduce frustration?
- Would it improve onboarding or time to value?
- Would it improve developer productivity?
- Would it improve reliability or trust?
- Would it differentiate the product meaningfully?
- Would it justify a subscription or expansion?
- Would it reduce operating or support cost without harming users?
- Is the value measurable?
- Is it more valuable than refining existing capabilities?

A proposal should normally be rejected, deferred, or reframed if it cannot answer at least one question strongly and has no credible strategic-enabling value.

Strategic-enabling work is acceptable when its causal path to user or commercial value is explicit.

4. predictable behavior;
5. integration quality;

7. performance;
8. polish;

Separate:

- leading indicators;
- lagging indicators;
- guardrail metrics.

Do not invent baselines.

## 15. Non-Goals and Strategic Boundaries

State what the product will not optimize for, including where appropriate:

- parity for its own sake;
- uncontrolled autonomy;
- feature volume;
- novelty without value;
- hidden or irreversible AI behavior;
- rewrites without evidence;
- ecosystem breadth at the cost of core quality;
- superficial demonstrations that do not survive production use.

## 16. Evolution and Governance

Explain:

- which principles are durable;
- which market observations require periodic review;
- what evidence can justify changing the vision;
- how changes should preserve repository truth and product continuity.

The vision must evolve through evidence, not fashion.

## 17. Writing Standard

Write like the internal product vision of a billion-dollar software company.

The document should be:

- clear;
- decisive;
- technically literate;
- commercially grounded;
- evidence-aware;
- durable;
- concise where possible;
- detailed where necessary;
- free of generic corporate filler.

Prefer:

- explicit tradeoffs;
- operational definitions;
- measurable outcomes;
- strong non-goals;
- repository-grounded reasoning.

Avoid:

- unsupported superlatives;
- vague statements such as “be better”;
- feature catalogs;
- competitor imitation;
- speculative architecture presented as commitment;
- marketing copy without operational meaning;
- claims that every priority is equally important.

Use normative language carefully:

- `must` for constitutional requirements;
- `should` for strong defaults;
- `may` for permitted options;
- `hypothesis` for directions requiring validation.

## 18. Interruption and Failsafe Protocol

If context, quota, tool access, or session time may prevent safe continuation:

2. Update `ENGINEERING_WORKSPACE.md`.
3. Record completed work.
4. Record all unfinished sections.
5. Record blockers and confidence limitations.
6. Record the exact next file and action.
7. Verify the checkpoint is machine-readable.
8. Verify no unauthorized files changed.
9. End the session without pretending the assignment is complete.

A future session must be able to resume using the repository and workspace alone.
